# 基准统计口径

## 新版解码脚本

`benchmarks/bench_decode.py` 整理自 10 月 GLM 基准，并修复如下统计问题：

1. 时钟在同发门控释放后启动，去掉旧脚本计入的约 0.3 秒人工等待。
2. TTFT 从第一条非空 `choices.text` 计时；usage、空 chunk 和结束标记不作为首字。
3. 输出 token 数只用 `usage.completion_tokens`。投机解码的 chunk 可能包含多个 token，缺失 usage 时该请求无效。
4. HTTP 错误、流式 error、零输出和缺失真实 token 数均记录失败。某轮有失败请求时不计算该轮吞吐，最终进程以非零状态结束。
5. 默认做同并发、同输出长度和近似同输入形状预热；正式轮输出 p50/min/max 与 spread。
6. 冷前缀模式在开头放随机标识，共享前缀模式只在尾部变化；二者结果分别保存。

冷前缀模式用于减少完整 prompt 重用，不能保证 cached_tokens 精确为零：tokenizer、短公共标记或外部缓存策略都可能影响命中。共享前缀模式也不保证百分之百命中。每请求的实际 usage 保留在 JSON 行中。

## 指标定义

聚合吞吐 = 同轮总 completion_tokens / 最长请求延迟。所有请求用同发门控，各请求时钟紧邻门控释放启动，但线程调度仍存在偏差；适合秒级服务测量，微秒级算子用 CUDA events/专门诊断。

每请求吞吐 = completion_tokens / 请求总延迟，包含 prefill 与首字等待。它不是排除 TTFT 的纯解码速度，也不是 TPOT。当前脚本输出每请求吞吐中位数以及 TTFT 中位数。

正式轮摘要的 `ttft_p50_of_p50_s` 是各轮请求中位数的中位数，不等于汇总所有请求的 P95。网关脚本的 P95 则是单轮请求样本按排序索引取得的经验分位数，小样本解释需谨慎。

## 历史数据

保留 JSON 来自原脚本，其计时在 gate.wait() 前启动，包含约 0.3 秒人工等待。历史 TTFT 和吞吐不可直接与修正后的脚本做绝对值比较。旧配置内部 A/B 仍可作为历史观测，但幅度受这段固定开销影响。

`results/infra-20261001/` 的 spread 使用 `(max-min)/min`；10 月 GLM 摘要和新版脚本使用 `(max-min)/median`。引用波动幅度时标明口径。

10 月 GLM 保留的是每档摘要，无法从它恢复每请求时序、token 数和环境竞争状态。9 月/10 月 infra 部分数据保留逐轮 JSON，但仍没有完整请求级记录。

## 正式复现建议记录

记录引擎源码 commit、镜像 digest、模型 revision、GPU/拓扑、驱动/CUDA/NCCL、命令行与相关环境变量；隔离生产流量、保存缓存状态和全部轮次，重复 A/B 次序，检查输出与工具调用。升级依赖或改变模型后重新测量。
