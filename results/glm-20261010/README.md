# 6～10 人 Agent 场景实机验证结果

日期：2026-10-10。所有生成请求均经过 new-api 入口及 glm-5.3-flash 路由；tokenize、健康检查和指标采集使用本机诊断接口。

生产状态：已恢复正常服务，new-api 路由检查通过。

## 采用的配置

生产只新增 `--long-prefill-token-threshold 1024`。MTP 仍为 4 个预测 token，最大上下文仍为 262144（输入与输出合计），max_num_seqs 仍为 16，总 token 预算及 LMCache chunk 均为 1152。此前注册心跳/重新注册修复保留。未部署固定 8 路的入口限制，未改动 new-api 管理配置。

## 多用户 Agent 工作流

每个模拟 agent 完成：模型发起 read_record 工具调用 → 模拟工具等待并返回数据 → 模型回答。常规输入约 2K～4K token，同时插入一条约 32K 冷输入。工具名称、参数、后续回答中的结果均检查通过。下表包含工具等待时间，反映两次模型调用组成的完整短任务。

| Agent 数 | 原配置任务耗时中位数 | 候选配置 | 减少 |
| --- | ---: | ---: | ---: |
| 6 | 18.37 秒 | 14.01 秒 | 23.7% |
| 8 | 20.16 秒 | 14.92 秒 | 26.0% |
| 10 | 22.96 秒 | 18.28 秒 | 20.4% |

模型调用首 token（包括思考/工具片段）的中位数，6/8/10 agent 分别从 8.32/9.18/10.55 秒降到 3.11/4.14/5.83 秒。工具调用收到完整参数后才进入工具阶段，未将半截工具 JSON 当成任务完成。

## 已有长生成时再提交输入

三轮中，先让 A 开始持续生成，2 秒后提交 B 的长输入，再过 0.5 秒提交短请求。原配置三轮均要等 A 结束，候选三轮均在 A 结束前开始返回长输入的输出。

| 指标 | 原配置 | 候选配置 |
| --- | ---: | ---: |
| 约 8K 输入首 token | 30.84 秒 | 4.00 秒 |
| 约 32K 输入首 token，第一轮 | 36.71 秒 | 14.86 秒 |
| 约 32K 输入首 token，第二轮 | 37.89 秒 | 14.89 秒 |
| 同时插入的短请求首 token，中位数 | 36.23 秒 | 1.22 秒 |
| 短请求首正文，中位数 | 38.39 秒 | 15.44 秒 |
| 短请求完整结束，中位数 | 39.54 秒 | 16.43 秒 |

**首 token 不等于首正文。**本次模型启用正常思考格式，首 token 可能是 reasoning；长输入计算期间，其他请求的输出间隔会增大，不能将 1.22 秒解读为完整回答或正文立即完成。两轮 32K 干扰请求达到人为设置的 512-token 输出预算，仅用于观察调度和首 token，未将这些截断回答作为内容正确性证据。

## 代价与适用范围

- 16K 单请求冷输入探针首 token 从 4.70 秒增加到 6.59 秒，约慢 40%；GPU 热前缀探针约为 0.35 秒，基本一致。分段增加了长输入的处理开销。
- 6/8/10 agent 混合负载中的长请求自身首 token 约从 14.90/16.03/18.21 秒增加到 19.58/20.83/23.03 秒；常规 agent 更早完成，长任务承担了部分代价。
- 原本持续生成的请求也可能变慢。相同 4096-token 输出的干扰实验中，A 的结束时间分别从 30.48→35.88 秒、30.86→46.26 秒；另外一轮候选自然提前结束于 2713 token，不能用该轮结束时间比较生成吞吐。
- 所有请求一起结束的时间没有稳定缩短，各轮生成量也不完全相同，因此本报告不宣称总吞吐提升。
- 这是少量、隔离、合成的代表性工作流验证；每个 agent 并发档一轮，交错长生成三轮。未据此宣称稳定 P95、长期 SLA 或完整真实代码任务质量。它支持修复入场饥饿并改善多数常规 agent 响应的结论。

## 缓存、边界与取消

- 同一约 16K 文档的冷请求、GPU 命中、CPU 回读均正确返回前部/中部/后部三个标记；CPU 回读实际传输了 16128 token。
- 截断到不同前缀深度后，CPU 回读探针分别实际传输了 4608 和 10368 token，并返回对应位置的正确标记。
- 1151/1152/1153/2303/2304/2305 个输入 token 的新前缀冷请求及重复请求共 12 次检查通过；新前缀的首次请求确认 cached_tokens=0。未发生零推进卡死。
- 原始边界夹具曾在 1024 输出预算内只生成思考；增加输出预算后返回正确答案。随后改用末尾指令更清晰、具有全新前缀的夹具，全部通过。原始失败保留在 candidate/diagnostics 中；没有将截断输出算作正确答案。
- 深度缓存探针首次严格字符串检查因答案附加加粗和引用而失败；核对实际标记正确后，改为检查所请求标记的有序集合，允许展示格式变化。保留初次请求记录，不把格式差异归类为缓存损坏。
- 经 new-api 取消流式生成后，基线和候选的后端活动请求均归零。
- 缓存状态均显示 4 个注册 worker；本次未新增一小时空闲测试，此前的隔夜存活证据仍适用于注册修复。

## 256K 上限与长输入

| 实际输入 token | 冷输入首 token | 三处标记检索 |
| ---: | ---: | --- |
| 65,559 | 26.45 秒 | 通过 |
| 131,107 | 54.25 秒 | 通过 |
| 260,142 | 115.30 秒 | 通过 |

260142 个输入 token 加上申请的 4096 个输出 token 超过 262144，new-api 返回 HTTP 400，确认总上下文上限被执行。长输入检索通过只代表这些合成样本，不能外推为所有长文档任务的质量保证。

## 8 路入口限制的探索

使用客户端 semaphore 模拟最多 8 条在途模型请求；排队时间计入任务耗时和端到端首 token。此实验不是 new-api 已实现的用户级公平调度，所有请求使用同一个测试凭据。使用新前缀避免复用前一个实验的缓存，少量提示 token 和输出差异仍存在。

| Agent 数 | 候选，未额外限制 | 候选，模拟最多 8 条在途 |
| --- | ---: | ---: |
| 8 | 14.92 秒 | 15.09 秒 |
| 10 | 18.28 秒 | 18.34 秒 |

这个小样本没有显示硬限 8 条的稳定收益，因此此次不部署这一限制。后续需要接入实际 user_id/task_id 才能实施调用方公平配额、子 agent 总预算和有限等待队列；这些入口功能没有在本次被宣称为已上线。

## new-api 与测试隔离说明

- 维护窗口使用临时 8000 端口代理，只接收实验标记请求；基线与候选模型均监听本机 8001，路由、代理和硬件保持相同。恢复生产时移除该代理，模型重新直接监听 8000。
- new-api 保留了 chat_template_kwargs，但过滤了 ignore_eos 和 prompt_logprobs。因此核查了 A 的实际输出长度；没有假定 ignore_eos 已生效。
- 为单独验证 CPU 回读，临时代理仅对保留的实验参数 max_tokens=1009 注入 prompt_logprobs=0，跳过本地前缀查询。该请求仍经过 new-api，但这个强制缓存路径是诊断干预，不代表 new-api 原生透传该字段。实际 external_kv_transfer 增量是回读证据。这个干预不用于比较普通请求延迟，且没有进入生产部署。
- enable_thinking=false 的初步探针仍生成思考文字，并混入正文；正式对比统一使用 enable_thinking=true，并区分 reasoning 与正文。未修改生产的全局思考策略。
